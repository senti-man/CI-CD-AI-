# CI/CD·AI 공급망 침해 대응 종합 프로젝트 제안서

**부제**: 오픈소스 기여자 위장 공격부터 SIEM 실시간 탐지·자동 대응까지 — Red Team vs Blue Team 라운드 방식으로 정량 검증

---

## 1. 한 줄 요약

CI/CD 파이프라인(Gitea/GitHub Actions)과 AI 생태계(패키지·MCP 서버·모델 파일)를 아우르는 4대 공급망 공격 벡터를 실제로 구축·재현하고, Wazuh SIEM 실시간 탐지·자동 대응·탐지 회피 라운드전을 거쳐 정량 지표(탐지율·오탐률·평균 대응시간)로 검증하는 프로젝트입니다.

## 2. 지금까지 실제로 구현하고 검증한 것 (진행 이력)

이 제안서는 아이디어 단계가 아니라, AI(Claude)와 함께 실제로 로컬 환경을 구축하고 두 차례에 걸쳐 끝까지 재현·검증한 결과를 바탕으로 씁니다. 어디까지 이미 됐고 어디부터가 앞으로 할 일인지 명확히 하기 위해, 진행 순서 그대로 기록해둡니다.

### 2-1. AI 공급망 공격 프로토타입 (`ai_supply_chain_demo/`)

로컬(127.0.0.1)에서만 동작하는 무해한 시뮬레이션으로 3가지 경로를 각각 구현하고 실행까지 확인했습니다.

- **악성 pip 패키지** (`ai-lint-helper`): `import` 되는 순간 정찰 정보 수집 + 가짜 비밀파일 읽기 + C2 서버 전송이 자동 실행되는 것을 실제로 확인
- **악성 MCP 서버** (`smart-code-formatter`): AI 에이전트가 "도구"를 호출하는 순간 동일한 방식으로 정보가 유출되는 것을 확인
- **오염된 pickle 모델 파일**: `__reduce__` + `exec` 트릭으로 `pickle.load()` 시점에 코드가 실행되는 것을 실제 파일로 만들어 확인
- **탐지 도구 2종**: YARA 스타일 문자열 매칭 도구(`mini_yara_matcher.py`), pickle opcode를 실행 없이 정적 분석하는 스캐너(`pickle_safety_scanner.py`) — 둘 다 정탐/오탐 결과까지 실측
- **타임라인 캡처 스크립트**(`capture_timeline.py`): 프로세스/네트워크/파일시스템/C2 로그를 통합해 시간순 타임라인(csv)으로 만드는 것까지 실행 확인
- **Wazuh 연동**: 이 PC에 Docker가 없던 시점이라 설계 문서와 룰 파일까지만 작성, 실제 배포는 미완료

### 2-2. CI/CD 파이프라인 PoC — 1차 구축 (AI가 자동으로 전 과정 실행)

Docker Desktop을 새로 설치(가상화 활성화 문제 해결 포함)한 뒤, Gitea + Actions Runner + 공격자 서버를 Docker로 띄우고 AI가 API/터미널로 전 과정을 한 번 자동 실행하며 검증했습니다.

- `demo-project` 저장소 생성 → 정상 워크플로우 push → Actions 정상 실행 확인
- 두 번째 계정으로 fork → curl로 위장한 악성 스텝("Setup build cache") 삽입 → PR 생성 → 병합
- **병합 후 약 6초 만에 등록해둔 가짜 시크릿이 실제로 공격자 서버 로그에 도착하는 것 확인**
- 탐지 스크립트를 표본 5개로 검증 (오탐 0%, 탐지율 100%)
- PR 자동 검사 게이트(Supply Chain Guard) 구현 → 새 위장 공격(wget)으로 재시도
- 게이트가 처음엔 아예 트리거되지 않는 문제를 발견 → 원인 조사 결과 "Gitea가 PR의 head(공격자 fork) 브랜치 기준으로 실행할 워크플로우를 판단한다"는 사실을 확인
- 공격자 브랜치에 upstream을 merge해 다시 시도 → 게이트가 정상적으로 `failure`로 반응
- 브랜치 보호 규칙을 걸어 병합 자체가 서버 단에서 거부되는 것(`HTTP 405`)까지 확인

### 2-3. 손으로 직접 재현한 실습 (2차 — 환경을 완전히 초기화하고 처음부터)

1차는 AI가 자동으로 진행한 것이었기 때문에, 팀원이 직접 손으로 실습할 수 있는지 검증하기 위해 Docker 컨테이너·볼륨·네트워크를 전부 삭제하고 완전히 처음부터 다시 진행했습니다. 이 과정에서 실제로 만난 문제와 해결 과정을 그대로 남겨둡니다 — 팀 온보딩 자료(18번 섹션)의 원재료입니다.

| 단계 | 겪은 문제 | 원인 / 해결 |
|---|---|---|
| Docker Desktop 최초 실행 | "Virtualization support not detected" | BIOS 문제가 아니라 WSL2/Virtual Machine Platform 기능 미설치가 원인. `wsl --install` 후 해결 |
| Actions Runner 등록 명령 | PowerShell에서 여러 줄로 나눠 쓴 `docker run` 명령이 줄마다 따로 실행되며 에러 | PowerShell은 줄 끝 `\`를 이어쓰기로 인식하지 않음 → 한 줄 명령으로 재작성 |
| 저장소 push | `remote: Failed to authenticate user` | Windows Git 자격증명 관리자(GCM)가 로컬 Gitea를 못 알아봄 → Personal Access Token을 URL에 직접 넣는 방식으로 해결 (demoadmin, attacker01 계정 각각 2회) |
| 악성 PR 생성 후 병합 | 워크플로우 자체가 실행되지 않음 | 웹 편집기에서 코드를 붙여넣을 때 들여쓰기가 깨져 YAML 문법 오류 발생 — 에러 메시지 없이 조용히 실패. 웹 UI에서 직접 재작성해 해결 |
| 시크릿 확인 | exfil 로그에 `secret=` 값이 비어 있음 | 저장소에 `FAKE_DEPLOY_TOKEN` 시크릿 등록을 빠뜨림 — 등록 후 재실행하여 **실제 값 유출 확인** |
| PR 병합 화면 | 병합 버튼 자체가 안 보임 | 브랜치 보호 규칙 없이도 Gitea가 실패한 Actions 체크에 대해 UI에서 병합 버튼을 숨기는 것을 발견 (API로는 정상 병합 가능함을 확인) |
| 2차 공격(wget 위장) 병합 | 브랜치 보호 규칙을 걸었는데도 병합이 그대로 성공함 | 필수 체크 이름을 `Supply Chain Guard / scan-workflows`로 등록했으나 실제 이름은 `...(pull_request)`였음 — 한 글자 차이로 보호가 조용히 무력화된 것을 직접 발견 |

이 표에 나온 문제들은 전부 **팀원 대부분이 그대로 겪을 가능성이 높은 것들**이라 `ONBOARDING.md`에 FAQ 형태로 미리 정리해뒀습니다.

## 3. 핵심 측정 지표 (먼저 정의)

발표에서 결국 말하게 될 숫자를 먼저 정하고, 나머지 설계는 이 숫자를 만들기 위해 역산했습니다.

| 지표 | 정의 | 현재 기준값 (기존 PoC 실측) | 목표 |
|---|---|---|---|
| 탐지율 (Recall) | 실제 악성 워크플로우/패키지 중 탐지에 성공한 비율 | 100% (n=5, curl·wget 위장 2종) | 표본 30개 이상, 회피 기법 포함 90% 이상 유지 |
| 오탐률 (False Positive Rate) | 정상 워크플로우를 악성으로 잘못 판단한 비율 | 0% (n=2) | 5% 미만 유지 |
| 평균 대응 시간 | 공격 트리거(병합)부터 대응 완료까지 걸리는 시간 | 탐지 없이 유출까지 약 6초 | Active Response로 유출 즉시(수 초 내) 자동 대응 |

## 4. 난이도를 이렇게 다시 잡은 이유

8명이 3주간 주 5일, 하루 8시간 이상 생성형 AI의 도움을 받아 작업한다고 가정하면 실질 작업량은 대략 **960인시(8명 × 15일 × 8시간)** 이고, 여기에 AI 보조로 구현 속도가 크게 붙습니다. 위 2번 섹션처럼 한 사람이 이틀 만에 로컬 Gitea PoC를 자동화로 한 번, 손으로 한 번 — 총 두 차례 끝까지 돌렸다는 걸 기준으로 잡으면, 이 정도 규모의 팀은 그 몇 배 분량을 3주 안에 소화할 수 있습니다. 그래서 아래처럼 범위를 넓혔습니다.

- **단일 시나리오 → 4대 벡터 통합**: CI/CD 파이프라인 + 악성 패키지 + 악성 MCP 서버 + 오염된 모델 파일
- **로컬 스크립트 탐지 → 실제 SIEM 구축**: Wazuh 매니저를 진짜로 띄우고 실시간 알림·자동 대응까지
- **일회성 공격 재현 → Red Team vs Blue Team 라운드전**: 매 라운드 새 회피 기법 vs 탐지율 개선을 숫자로 추적
- **표본 5개 → 최소 30~50개 표본 + 정밀도/재현율 정량 평가**
- **Gitea 단일 플랫폼 → 실제 GitHub(비공개 테스트 조직)에서도 재현해 플랫폼 종속성 여부 검증**
- **스크립트 수준 도구 → 실제 재사용 가능한 GitHub/Gitea Action으로 패키징**

## 5. 이 제안서를 이렇게 설계한 원칙

주제를 다듬으면서 스스로에게 반복해서 던진 질문들을 그대로 적어둡니다. 다른 아이디어를 검토할 때도 똑같이 써먹을 수 있는 체크리스트입니다.

1. **"우리가 뭘 만들지"가 아니라 "기존 방식의 어디가 구체적으로 뚫리는지"에서 출발했는가?**
   이 프로젝트는 "공급망 공격을 재현하자"에서 멈추지 않고, PR 리뷰·탐지 스크립트·브랜치 보호 규칙 각각이 정확히 어느 지점에서 실패하는지를 실제로 뚫어보면서 찾았습니다 (2번, 15번 섹션).
2. **측정할 숫자를 먼저 정하고, 그 숫자를 만들기 위해 파이프라인을 역산해서 설계했는가?**
   탐지율·오탐률·평균 대응시간 세 가지를 3번 섹션에 먼저 정했고, Red Team vs Blue Team 라운드전은 이 숫자를 라운드마다 갱신하기 위한 장치입니다.
3. **하지 않을 것을 명시했는가?**
   17번 섹션에 명시했습니다. 범위를 넓힌 것과 무한정 확장하는 것은 다릅니다.
4. **역할을 개발 부담 수준으로 계층화해서, 모든 인원이 실질적으로 기여할 자리가 있는가?**
   19번 섹션 역할 분담표에 부담 수준을 같이 표시했습니다.

## 6. 프로젝트 범위 — 4대 공급망 공격 벡터

| 벡터 | 트리거 | 담당 |
|---|---|---|
| ① CI/CD 파이프라인 탈취 | PR 병합 시 워크플로우 자동 실행 | A팀 |
| ② 악성 오픈소스 패키지 | `pip install` 후 `import` | B팀 |
| ③ 악성 MCP 서버 | AI 에이전트의 도구 호출 | B팀 |
| ④ 오염된 AI 모델 파일 (pickle) | `pickle.load()` | B팀 |

①은 2번 섹션에 정리했듯 이미 실제로 두 차례(자동화 1회 + 손으로 직접 1회) 공격→탐지→병합 차단까지 전 과정을 검증했고, ②③④는 별도 로컬 시뮬레이션(C2 서버 포함)으로 이미 프로토타입이 동작하는 상태입니다. 3주 프로젝트는 이 네 가지를 **하나의 공격자 인프라**(같은 C2)로 통합하고, 7~11번 항목으로 깊이를 더하는 데 씁니다.

## 7. 확장 목표 1 — Wazuh 실시간 SIEM 구축

기존에는 탐지 로직을 로컬 스크립트로만 검증했습니다. 이번엔 실제로 Wazuh Manager + Dashboard를 띄워서:

- 4대 벡터 각각의 IoC(C2 통신, 의심 커밋, 파일 변경)를 실시간 알림으로 연결
- MITRE ATT&CK 탭에서 실시간으로 공격 단계가 매핑되는 것을 라이브 시연
- **Active Response 자동 대응**: 알림 발생 시 Gitea API를 호출해 유출된 시크릿을 자동 폐기·재발급하거나, 악성 PR을 자동으로 닫는 스크립트까지 연결 (탐지에서 끝나지 않고 "탐지 → 자동 대응"까지 보여주는 게 핵심)

## 8. 확장 목표 2 — Red Team vs Blue Team 라운드전

팀을 공격팀/방어팀으로 나눠 라운드제로 운영합니다.

1. 공격팀이 새로운 위장/회피 기법으로 워크플로우(또는 패키지·모델 파일)를 변형해 제출
2. 방어팀은 기존 탐지 로직으로 먼저 스캔 → 놓치면 로직을 보강
3. 라운드마다 **탐지율 변화를 기록** (예: 1라운드 60% → 5라운드 95%)
4. 최종 발표에서 "라운드별 탐지율 추이 그래프"로 방어 로직이 실제로 성장한 과정을 정량적으로 제시

회피 기법 예시: base64 인코딩, 여러 스텝에 분산 삽입, `env:`에 시크릿을 먼저 옮겨 담고 나중에 참조, 정상 액션 뒤에 숨기기(서드파티 액션 자체를 오염시키는 것도 가능) 등. 15번 섹션의 "우회 방법" 열이 그대로 라운드전 소재가 됩니다.

## 9. 확장 목표 3 — 플랫폼 일반화 검증

지금까지는 로컬 Gitea 하나로만 검증했습니다. 같은 공격이 **실제 GitHub**(반드시 비공개 테스트 조직 + 가짜 시크릿만 사용)에서도 동일하게 통하는지 재현해서, "이게 우리가 만든 로컬 환경의 특이 케이스가 아니라 CI/CD 플랫폼 전반의 구조적 문제"라는 걸 증명합니다. 2번 섹션에서 발견한 두 가지(① fork PR엔 시크릿이 기본적으로 안 넘어감, ② 새로 추가한 방어 게이트가 기존 fork에는 소급 적용 안 됨)가 GitHub에서도 똑같이 재현되는지 확인하는 것만으로도 좋은 비교 실험이 됩니다.

> ⚠️ 실제 GitHub을 쓸 경우 반드시 팀 전용 비공개 조직에서, 가짜 시크릿만 사용하고, 실습 종료 후 조직/저장소를 삭제해야 합니다. 실제 서비스 계정이나 진짜 크리덴셜은 절대 사용하지 않습니다.

## 13. 이미 발견한 실전 함정 (재사용 가능한 강점)

1. **소급 적용 한계**: 방어 게이트를 새로 추가해도 그 이전에 갈라져나온 공격자 fork에는 자동 적용되지 않음 (head 브랜치 기준으로 워크플로우 평가)
2. **플랫폼 기본 방어 확인**: fork PR 빌드에는 시크릿이 기본적으로 노출되지 않음 → 진짜 위험 구간은 "병합 이후"
3. **문자열 불일치로 인한 보호 무력화**: 브랜치 보호 규칙의 체크 이름이 실제 이름과 한 글자만 달라도 조용히 무시됨
4. **CI 실행 환경 자체의 함정**: PEP 668 pip 정책, stdout 버퍼링, YAML 들여쓰기 오류로 인한 무음 실패 등
5. **UI와 API의 동작 차이**: 브랜치 보호가 없는 상태에서 실패한 체크가 있으면 Gitea 웹 UI는 병합 버튼을 숨기지만, API로는 그대로 병합이 가능함 (2-3번 섹션)

## 14. 대응책 → 우회 → 재대응 (층별 정리)

방어는 한 겹으로 끝나지 않습니다. 각 층의 대응책이 뚫리는 지점과 그다음 겹을 정리했습니다. Red Team vs Blue Team 라운드전(8번 섹션)의 뼈대이자, 발표에서 "결국 완벽한 방어는 없고 계속 갱신되는 군비경쟁"이라는 메시지로 이어지는 핵심 자료입니다.

### 1층 — 사람이 리뷰

| 대응책 | 우회 방법 | 재대응책 |
|---|---|---|
| PR 리뷰 필수화 | 리뷰어 피로/신뢰, 또는 정상 PR을 여러 번 올려 신뢰를 쌓은 뒤 슬쩍 끼워넣기 | 워크플로우 경로 변경엔 보안 담당자 지정 리뷰 강제(CODEOWNERS), 기여 이력 짧은 계정의 워크플로우 변경은 자동 보류 |

### 2층 — 정적 탐지 (기존 PoC에서 구현)

| 대응책 | 우회 방법 | 재대응책 |
|---|---|---|
| 정규식/구조 기반 탐지(네트워크 명령 + 시크릿 참조 동시 등장 시 플래그) | ① base64/hex 인코딩 후 디코드 실행 ② 여러 스텝에 값을 나눠 조합 ③ `run:` 블록이 아니라 참조하는 서드파티 액션 내부에 유출 로직을 숨김(현재 탐지기는 `run:` 블록만 검사) ④ URL을 런타임에 동적으로 조립 | 참조 액션까지 재귀적으로 스캔, 액션을 태그가 아닌 커밋 SHA로 고정(pin), "동적으로 조립된 명령어" 자체를 의심 신호로 취급 |

### 3층 — 브랜치 보호 / 필수 상태 체크 (기존 PoC에서 구현)

| 대응책 | 우회 방법 | 재대응책 |
|---|---|---|
| 필수 상태 체크 통과 시에만 병합 허용 | ① 체크 이름 미스매치(실제로 겪음) ② 새 fork엔 소급 적용 안 됨(실제로 겪음) ③ 악성 PR이 같은 커밋에서 게이트 워크플로우 파일 자체를 삭제/이름변경 — 체크가 "미실행" 상태가 되면 플랫폼에 따라 병합이 통과될 수 있음(검증 필요한 가설) ④ 관리자 강제 병합 권한 | 워크플로우 파일 자체도 CODEOWNERS로 보호, "관리자 우회 금지" 옵션 활성화, 체크 미실행 상태에서도 안전하게 막는지 명시적으로 테스트 |

### 4층 — 시크릿 설계

| 대응책 | 우회 방법 | 재대응책 |
|---|---|---|
| 장기 시크릿 대신 OIDC 단기 토큰, 최소 권한 부여 | OIDC 신뢰 정책이 "이 저장소의 아무 브랜치/PR"처럼 느슨하면 여전히 아무 PR에서나 토큰 발급 가능 | 신뢰 조건을 특정 브랜치/환경으로 제한, 프로덕션 시크릿은 환경 보호 규칙으로 사람 승인 추가 |

### 5층 — 네트워크/런타임 통제

| 대응책 | 우회 방법 | 재대응책 |
|---|---|---|
| 러너 아웃바운드를 화이트리스트로 제한 | 이미 허용된 도메인을 악용 (GitHub API로 이슈/코멘트에 시크릿 남기기, gist 업로드 등 "living off the land") | 목적지 화이트리스트뿐 아니라 트래픽 내용 검사(DLP), 빌드 단계와 시크릿이 필요한 배포 단계를 분리 |

### 6층 — SIEM/실시간 탐지 (확장 목표 1)

| 대응책 | 우회 방법 | 재대응책 |
|---|---|---|
| 실시간 알림 | 병합~유출이 약 6초 — 사람이 알림을 보고 반응하기엔 이미 늦음 | 알림에서 끝내지 않고 Active Response로 탐지 즉시 시크릿 자동 폐기까지 파이프라인화 |

### 메타 층 — 방어 도구 자체도 공급망

탐지 스크립트, Wazuh 룰, 리뷰 프로세스 전부 결국 사람이 관리하는 소프트웨어입니다. 이 방어 체계 자체(또는 이를 관리하는 계정)가 침해당하면 모든 층이 함께 무너집니다. 성숙한 조직은 방어 도구 자체에 서명(SLSA/provenance)을 걸어 "이 방어를 우회하려면 방어 시스템 자체를 먼저 뚫어야 한다"는 이중 잠금을 씁니다.

## 21. 진행 시 주의사항

- 실제 GitHub을 쓰는 실험은 반드시 비공개 테스트 조직 + 가짜 시크릿으로만 진행하고, 종료 후 정리합니다.

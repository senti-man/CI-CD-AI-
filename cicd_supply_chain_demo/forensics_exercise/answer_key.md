**A2.**

- 데이터를 보내는 목적지는 `http://attacker-server:8000/exfil`. 이 저장소가
  정상적으로 통신할 이유가 없는 낯선 호스트입니다.
- 종합하면 악성 코드로 보는 게 맞습니다. 근거는 네 가지입니다. 스텝 이름과
  실제 동작이 다르다는 것, 빌드나 테스트와 아무 상관없이 시크릿을 외부로

  이 스텝의 실행 결과를 뒤에 오는 어떤 스텝도 쓰지 않는다는 것 — 진짜
  캐시였다면 있어야 할 후속 활용이 전혀 없습니다.

**A3.** PR을 연 사람은 `attacker01`, 병합한 사람은 관리자 `demoadmin`입니다.

시크릿에 접근할 권한이 전혀 없었지만, 관리자가 병합하는 순간 관리자의
권한(시크릿에 접근 가능한 CI 환경)으로 공격자의 코드가 돌아간 겁니다.

## Part 2

**A7.** 커밋 순서대로 정리하면 이렇습니다.
1. `security: add Supply Chain Guard to auto-scan workflow changes after
   incident` — 사고를 인지한 뒤 자동 탐지 게이트를 저장소에 추가
2. `security: remediate - remove malicious 'Setup build cache' step from
   build.yml` — 악성 스텝을 지우고 파일을 원래대로 되돌림
3. `fix: use --break-system-packages for pip install on PEP 668 ubuntu
   images` — 게이트 자체가 실행 중 에러 나던 걸 고침
4. `fix: drop unreliable paths filter on pull_request trigger` — 게이트의
   트리거 조건을 손봄

**A8.** 이 요청들은 `attacker01`이 그다음에 시도한 두 번째 공격(`wget`
기반, 이번엔 `Cache node_modules`라는 이름으로 위장)이 아직 병합되지 않은
PR 상태에서 `pull_request` 이벤트로 실행되면서 나온 겁니다. 시크릿 값이
비어있는 건 우연이 아니라, Gitea(그리고 GitHub 같은 대부분의 플랫폼)가
fork에서 들어온 `pull_request` 이벤트에는 기본적으로 저장소 시크릿을 안
내주도록 만들어져 있기 때문입니다. 이건 정확히 지금 우리가 다루는 것 같은
공격 — 낯선 기여자가 PR만 열어도 시크릿을 훔쳐갈 수 있는, 흔히 pwn
request라고 부르는 취약점 — 을 막으려고 플랫폼 차원에서 걸어둔 기본
방어입니다. 그래서 이 사고에서 시크릿이 실제로 새어나간 경로는 딱 하나,
"병합돼서 main 브랜치에서 push 이벤트로 실행됐을 때"뿐이었다는 게 이
로그로 증명됩니다.

**A9.**
- 필수로 걸린 체크는 `Supply Chain Guard / scan-workflows (pull_request)`.
- 이게 막을 수 있는 건, 이 체크가 실패한 PR은(관리자가 규칙을 우회하지
  않는 한) 병합 자체가 거부된다는 겁니다(`HTTP 405 Not all required
  status checks successful`). 리뷰어가 놓치더라도 자동으로 병합을
  막아주는 안전망인 셈입니다.
- 못 막는 것도 있습니다. 첫째, 게이트 워크플로우가 공격자의 fork/브랜치에
  아직 없으면(업스트림에 막 추가된 직후, 그보다 먼저 갈라져나간 브랜치라면)
  애초에 트리거가 안 돼서 아무것도 못 막습니다 — 이 실습에서 실제로
  재현된 문제입니다. 둘째, A8에서 봤듯 PR 자체의 빌드가 도는 것까지는
  막지 못합니다. 만약 플랫폼의 fork-시크릿 격리가 없었다면 병합 전에도
  유출이 가능했을 거란 얘기죠. 결국 이 게이트는 여러 방어선 중 하나일
  뿐이지 유일한 방어선은 아닙니다.

**A10.** PR #2는 `closed`, PR #3은 `open`(이후 브랜치 보호 규칙에 막혀
병합은 거부됨) 상태이고, 둘 다 같은 브랜치(`chore/cache-node-modules`)에서
나왔습니다. `attacker01`이 #2를 닫고 #3을 새로 연 이유는 실습 중 실제로
확인된 사실과 맞닿아 있습니다. 이미 열려 있던 PR에 커밋만 추가
(synchronize)하는 걸로는 게이트 워크플로우가 트리거되지 않았고, PR을 아예
새로 만들어야 Gitea가 트리거 대상 워크플로우 목록을 다시 평가했습니다.
실전이라면 공격자가 이 특성을 "탐지를 피해가는 시행착오" 삼아 악용할
수도 있다는 뜻이기도 합니다.

## Part 3 — 보고서 예시

**사고 원인**: 신뢰되지 않은 외부 기여자가 정상적인 기능 개선처럼 위장한
PR로 CI 워크플로우 정의 파일에 시크릿 유출 코드를 심었고, 유지관리자가
이를 알아채지 못한 채 병합하면서 배포 시크릿이 외부로 새어나갔습니다.

**영향 범위**: `FAKE_DEPLOY_TOKEN` 1건 유출(실환경이라면 이 크리덴셜로
접근 가능한 모든 배포·인프라 자원이 잠재적 영향 범위입니다). 이번
사고에서는 탐지/원복 전까지 로그상 2회(최초 병합 시 1회, 재검증 목적의
재실행 1회) 유출이 확인됐습니다.

**탐지 방법**: 이번엔 사후적으로, 로그를 확인하고서야 발견했습니다. 개선
방안으로는 PR 리뷰 시 `.gitea/workflows/**` 변경분을 따로 강조해서 보여주는
리뷰 정책, 이번에 만든 자동 스캔 게이트를 병합 이전 시점에 확실히
강제하는 것, 시크릿 사용 로그와 아웃바운드 네트워크 로그를 실시간으로
모니터링하는 것(Wazuh 같은 SIEM 연동) 정도를 꼽을 수 있습니다.

**대응 조치**: 악성 스텝 제거(원복), 자동 탐지 게이트 추가, 브랜치 보호
규칙으로 필수 체크 강제. 여기에 더해 유출된 시크릿은 즉시 폐기하고
재발급해야 하고, 그 시크릿으로 접근 가능했던 시스템에 별도로 침해 여부를
점검해봐야 합니다.

**재발 방지 대책**:
1. `.gitea/workflows/**` 변경이 포함된 PR은 관리자 2인 이상 리뷰와 자동
   스캔 게이트 통과를 둘 다 병합 조건으로 강제합니다 (브랜치 보호 규칙에
   리뷰어 승인 조건 추가)
2. 신규이거나 신뢰도가 낮은 기여자의 PR은 워크플로우 파일이 바뀌면
   자동으로 실행을 보류하고 승인을 받게 합니다
3. CI 시크릿은 최소 권한으로 발급하고 주기적으로 로테이션하며, 가능하면
   OIDC 기반 단기 토큰으로 옮겨가서 장기 시크릿 자체를 최소화합니다
